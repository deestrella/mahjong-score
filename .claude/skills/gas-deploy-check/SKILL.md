# GAS(中継役)を変えるときの手順

このページは 2 か所で公開されていて、反映のされ方が違います。ここを取り違えるのが一番の事故のもとです。

| | 反映のしかた | Claude ができること |
|---|---|---|
| ページ(`index.html`・`assets/`) | `main` に push すると 1〜2 分で反映 | 編集・テスト・push |
| GAS(`gas/`) | GAS の画面で**新バージョンをデプロイ**したときだけ反映 | 編集まで。デプロイは**ユーザーにしかできません** |

GAS のデプロイには、持ち主の Google アカウントでのログインが要ります。このセッションには `clasp` もログイン情報もありません。なので、`gas/` を変えたら「ユーザーにデプロイしてもらう」ところまでが作業です。ここを伝え忘れると、リポジトリは新しいのに公開中の GAS は古いまま、という状態が誰にも気づかれずに続きます。

## 1. 変える前に: 触ってはいけないものを確かめる

- `GEMINI_API_KEY` と `PASSPHRASE` の**値**は、コード・コメント・コミットメッセージ・会話のどこにも書きません。値は GAS のスクリプトプロパティにだけあります。新しい設定が要るときは、プロパティの**名前**だけを決め、値はユーザーに GAS の画面で入れてもらいます。
- `gas/appsscript.json` の `webapp`(`executeAs`・`access`)は、ページから匿名で呼べるようにするための設定です。変えると全員が使えなくなることがあるので、変える前にユーザーに確認してください。
- `API_URL`(`assets/app.js`)は公開して問題ありません。「新バージョン」でデプロイする限り URL は変わらないので、ふつうは触りません。

## 2. ページと GAS の約束事を崩さない

ページと GAS は同時には更新されません。push したページが先に公開され、GAS は持ち主がデプロイするまで古いままです(逆の順もあります)。なので、**どちらが先でも動く**ように変えます。

- 項目を**足す**のは安全です(相手が知らない項目は無視されます)。ページ側では、新しい項目が無くても動くように書きます(`j.t || null` のように)。
- 項目の**名前を変える・消す**、意味を変えるのは避けます。どうしても必要なら、しばらく古い名前と新しい名前の両方を受け付けます。
- GAS で新しいエラーの種類(`error: 'xxx'`)を足したら、`assets/app.js` の `ERR` にも日本語の文言を足します。です・ます調で短く、利用者が次に何をすればよいか分かる文にします。`ERR` に無いと、利用者には意味の分からない表示になります。

いまの約束事:
- ページ → GAS: `{ pass, prompt, images: [{ mimeType, data }], hq }`(POST、`text/plain`)
- GAS → ページ: `{ result, t: { gas, ai, model, tries } }`、または `{ error, message? }`
- `doGet()` は `{ ok: true, message }` を返す(動いているかの確認用)

## 3. 変えたあとに自分で確かめる

GAS 自体はここでは動かせませんが、偽物の上でなら動かせます。次の 2 つを実行します。

```bash
cp gas/Code.gs "${TMPDIR:-/tmp}/Code.js" && node --check "${TMPDIR:-/tmp}/Code.js"
```

```bash
node .claude/skills/gas-deploy-check/scripts/try-gas.mjs
```

1 つ目は文法の確認です。文法の誤りがあると、デプロイしても GAS が動きません。

2 つ目の `try-gas.mjs` は、`UrlFetchApp`・`PropertiesService` などの偽物を用意して `doGet` / `doPost` を実際に動かします。偽の Gemini の返答を使うので、本物の Gemini には送りません。API キーも回数制限も使いません。今の約束事(ふつうの読み取り・合言葉違い・回数の上限・429・混雑時の切り替え・キー無し)の確認が入っています。

**変えた部分の確認は、`checks` に 1 行足してから実行します。** たとえば新しいエラーを返すようにしたなら、そのエラーになる偽の返答を `replies` に入れ、期待するエラーが返るかを確かめます。足した確認も残しておくと、次に GAS を直すときにまとめて確かめられます。

- `assets/app.js` も変えたなら `npm test` を通します(写真の読み取りはテストされませんが、ページが壊れていないかは分かります)。
- 変更を読み直し、`UrlFetchApp`・`PropertiesService`・`LockService` など GAS にしかない仕組みの使い方が正しいかを確かめます。`LockService` で取ったロックは `finally` で必ず放します。

## 4. ユーザーにデプロイの手順を伝える

報告の最後に、次の手順を**そのまま実行できる形で**書きます。毎回省略せずに書くのは、デプロイがたまにしかない作業で、手順を忘れやすいからです。

> **GAS の更新をお願いします**(このままだと公開中の GAS は古いままです)
> 1. script.google.com を持ち主のアカウントで開き、「麻雀点数 中継」を開きます。
> 2. `gas/Code.gs` の中身を、エディタの `Code.gs` にまるごと貼り付けて保存します。clasp を使う場合は `clasp push` です。
> 3. 「デプロイ」→「デプロイを管理」→ 鉛筆のアイコン →「バージョン」で**新バージョン**を選び、「デプロイ」を押します。
> 4. 公開 URL をブラウザで開き、`麻雀点数早見の中継は動いています。` と出ることを確かめます。
> 5. ページで写真を 1 枚読み取って、結果が出ることを確かめます。

「新しいデプロイ」を選ぶと URL が変わってしまいます。必ず「デプロイを管理」から**既存のデプロイを新バージョンにする**よう書いてください。新しいスクリプトプロパティを使う変更なら、手順 3 の前に「プロジェクトの設定 → スクリプト プロパティ」で名前と値を入れる手順も足します(値は書かずに、名前と意味だけ)。

## 5. 公開中の GAS が動いているか確かめたいとき

「写真の読み取りが動かない」「反映されない」と言われたら、まず公開 URL に GET してみます。

```bash
curl -sSL -m 20 "$(grep -o "https://script.google.com/macros/s/[^']*" assets/app.js)"
```

- `{"ok":true,...}` が返れば GAS は動いています。問題はページ側か Gemini 側です。
- `CONNECT tunnel failed, response 403` は、このセッションのネットワーク設定で script.google.com に出られないという意味です。GAS が止まっているわけではありません。ユーザーに URL をブラウザで開いてもらい、表示を教えてもらってください。
- 公開 URL に POST は送りません。写真が無くても、合言葉が未設定なら回数を 1 回使い、Gemini も呼んでしまいます。GAS の処理を確かめたいときは `try-gas.mjs` を使います。

## 6. 報告する

- 何を変えたか。ページ側も変えたかどうか。
- `node --check`・`try-gas.mjs`(と `npm test`)の結果。足した確認があればその名前も
- **デプロイ待ちであること**と、4 の手順
- ページ側も変えた場合は、どちらを先に公開しても動くか。動かない場合は、どちらを先にすべきか。

`main` への push は、ユーザーに頼まれたときだけ行います。GAS 側の変更がまだデプロイされていないときは、その旨も添えます。
